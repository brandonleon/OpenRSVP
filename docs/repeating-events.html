Recurring series

Repeating Events

Schedule daily, weekly, biweekly, or monthly occurrences from a single form.

Series Multi-occurrence

How it works

When you tick the Repeat dropdown during event creation, OpenRSVP generates all occurrences at once and groups them under a shared series.

  • Each occurrence is a fully independent event with its own RSVP page and admin link.
  • RSVPs, messages, and capacity limits are per-occurrence—guests RSVP to a specific date, not the whole series.
  • All occurrences inherit the title, description, location, channel, and privacy settings of the original form.

Nothing special is required on the guest side. Sharing works the same as any other event—send the RSVP link for the specific date.

Recurrence options

RuleInterval
daily+1 day per occurrence
weekly+7 days per occurrence
biweekly+14 days per occurrence
monthlySame day of each month (day clamped for shorter months)

Set the number of occurrences (2–52, inclusive of the first event). For example, "weekly · 8 occurrences" creates 8 Wednesday-night events spaced 7 days apart.

Series admin page

After creation, a series admin link is shown at:

/series/<series-id>/admin/<series-token>
  • Lists every occurrence in chronological order with RSVP counts and attendance totals.
  • Quick links to each occurrence's own admin page and public RSVP page.
  • Shows the recurrence rule (e.g., "Repeats weekly").
Keep this link private. Anyone with the series admin token can navigate to every occurrence's admin page.

Per-occurrence admin

Each occurrence has its own admin page at /e/<event-id>/admin/<admin-token>. The page shows a "Part of a series →" badge that links back to the series overview.

  • Edit details, close RSVPs, or delete a single occurrence without affecting sibling events.
  • RSVP close schedules are offset automatically—if you set an auto-close 1 hour before the first event's start, every occurrence will auto-close 1 hour before its own start.
  • Max-attendee caps apply per occurrence, not across the whole series.

Data model & decay

Under the hood, a series is an EventSeries record with a unique admin_token and a recurrence_rule string. Each Event row carries an optional series_id FK.

  • Series occurrences decay and clean up independently. An occurrence that passes its event date will score-decay on the same schedule as any single event.
  • Deleting one occurrence only removes that event and its RSVPs; the series record and other occurrences are unaffected.
  • The EventSeries row is not automatically deleted when all occurrences are gone—future cleanup may prune orphaned series rows.

The Alembic migration 0003_repeating_events creates the event_series table and adds a nullable series_id column to the events table.

What doesn't propagate across a series

Because occurrences are independent events, changes made after creation are not automatically mirrored to sibling events. To update all occurrences you must edit each one individually (use the series admin page for quick navigation).

Set at creation time (shared origin)

  • Title, description, location
  • Channel and visibility
  • Admin approval requirement
  • Max attendees
  • RSVP close schedule (offset per occurrence)

Independent per occurrence

  • RSVPs and messages
  • Admin token and RSVP close state
  • Edits made post-creation
  • Decay score
  • Deletion
